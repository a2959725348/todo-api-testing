# 缺陷记录

> 这份记录只写**真实发现并跟踪过**的问题，包括测试框架自身的缺陷和被测试服务的缺陷。
> 每一条都遵循「现象 → 复现步骤 → 定位分析 → 修复验证」的结构，这也是实际工作中提交缺陷单的写法。

## BUG-01 用例数据不隔离，导致第二次执行全部失败

| 字段 | 内容 |
| --- | --- |
| 发现阶段 | 接口自动化用例首轮全绿后，原样再跑一遍 |
| 严重等级 | 严重 |
| 缺陷类型 | 测试代码缺陷 |
| 状态 | 已修复并验证 |

**现象**

首次执行 `pytest` 时 45 条用例全部通过；不重启服务直接再跑一次，出现 3 条失败：

```
FAILED testcases/test_register.py::TestRegister::test_register_parameterized[用户名最短边界_3位]
AssertionError: 状态码不符：期望 201，实际 400；响应体={"msg":"用户名已被占用"}
```

**复现步骤**

1. 启动被测服务，执行 `pytest` → 45 passed
2. 保持服务运行，再次执行 `pytest` → 3 failed

**定位分析**

用例里用的是写死的用户名（如 `user_normal_01`），而服务数据存在内存、不会自动清空。第二遍执行时这些账号已存在，注册接口正确返回「用户名已被占用」，于是「期望 201」的断言失败。

问题不在被测服务，而在**用例之间、用例与执行轮次之间没有做数据隔离**——这是自动化测试最常见的坑之一。

**修复**

1. 不关心用户名的用例改用 `uuid` 生成唯一账号，天然可重复执行；
2. 被测服务增加一个仅在 `TEST_MODE=1` 时开放的 `POST /api/_test/reset` 接口，pytest 会话开始时清空一次数据；
3. 长度边界类用例必须保留固定长度，因此依赖第 2 步的会话级数据重置。

**验证**

连续执行 3 遍，均为 `45 passed`，耗时稳定在 6 秒左右。

## BUG-02 UI 异步重渲染导致元素失效（StaleElementReferenceException）

| 字段 | 内容 |
| --- | --- |
| 发现阶段 | UI 自动化首轮执行 |
| 严重等级 | 严重 |
| 缺陷类型 | 测试代码缺陷 |
| 状态 | 已修复并验证 |

**现象**

9 条 UI 用例中 2 条失败，报错：

```
selenium.common.exceptions.StaleElementReferenceException: Message: stale element reference: element is not attached to the page document
```

失败用例：`test_toggle_marks_item_done`、`test_delete_removes_item`。

**复现步骤**

1. 登录后新增一条待办
2. 立即对该条目执行勾选或删除
3. 报 StaleElementReferenceException

**定位分析**

前端每次增删改后都会重新请求列表并整体重建 `<ul>` 的子节点。用例先拿到条目元素句柄，再去点击，此时原节点已被销毁、替换为新节点，句柄失效。

初级写法通常是加 `time.sleep(1)` 糊过去，但这不是修复：它把「等某个状态出现」偷换成「等固定时间」，网络或机器慢一点照样失败，而且拖慢整体执行。

**修复**

1. 新增 `BasePage` 基类，实现 `retry()` 与 `wait_until()` 两个原语，自动吞掉 `StaleElementReferenceException` / `NoSuchElementException` / `IndexError` 并重试；
2. 所有取值走 `retry`（元素失效就重新定位），所有状态变化走 `wait_until`（必须等到条件成立）；
3. 用例里彻底移除 `sleep`。

修复过程中还踩到一个语义坑：初版 `retry` 把「返回空列表」当成「还没准备好」，导致「断言列表为空」的用例永远等不到结果而超时。因此把两种语义拆成两个方法——**空列表是合法取值，不是未就绪**。

**验证**

连续执行 2 遍，均为 `9 passed`，耗时约 30 秒。

## BUG-03 标题长度边界用例的数据长度不准确

| 字段 | 内容 |
| --- | --- |
| 发现阶段 | 编写 `data/todo_cases.yaml` 时自检 |
| 严重等级 | 一般 |
| 缺陷类型 | 测试数据缺陷 |
| 状态 | 已修复并验证 |

**现象**

「标题最长边界_50位」「标题超长_51位」两条用例的中文标题，实际长度分别是 33 和 34 个字符，根本没有触达 50 位边界。

若照原样执行，前者会通过（但**验证的不是边界**），后者会失败——因为 34 位属于合法长度，接口返回 201 而用例期望 400。

**定位分析**

中文标题靠肉眼数很容易出错，凭感觉拼字符串无法保证长度精确。

**修复**

用脚本生成精确 50 / 51 个字符的字符串，写入 YAML 前先校验 `len()`：

```python
base = '这是一个需要检查长度边界的待办标题用来验证接口的入参校验逻辑是否正确'
t50 = (base * 5)[:50]   # len == 50
t51 = (base * 5)[:51]   # len == 51
```

**验证**

两条用例分别返回 201 和 400，且错误提示为「标题长度需为 1-50 个字符」，边界行为正确。

**改进**

边界值用例的数据长度应当由程序保证，而不是人眼核对——这条经验已写入用例设计规范。

## BUG-04 登录凭证永不过期

| 字段 | 内容 |
| --- | --- |
| 发现阶段 | 设计鉴权用例时，尝试构造「过期 token」场景 |
| 严重等级 | 一般 |
| 缺陷类型 | 安全类设计缺陷 |
| 状态 | 已知未修复（演示服务刻意简化） |

**现象**

token 由 `user_id + HMAC 签名` 生成，不含任何时间信息。同一账号无论间隔多久登录，拿到的 token 完全相同，且一旦签发永久有效。

**影响**

- 无法实现「登录有效期」，token 泄露后长期可用；
- 无法测试「凭证过期」这个鉴权场景，用例只能覆盖「未携带」和「伪造」两种情况。

**建议**

token 中加入 `exp` 时间戳并参与签名，校验时比对当前时间；同时补充对应的过期场景用例。

## BUG-05 待办列表无分页，数据量大时全量返回

| 字段 | 内容 |
| --- | --- |
| 发现阶段 | 评审接口设计时 |
| 严重等级 | 一般 |
| 缺陷类型 | 功能设计缺陷 |
| 状态 | 已知未修复（演示服务刻意简化） |

**现象**

`GET /api/todos` 无任何分页参数，一次性返回当前用户全部待办。

**影响**

待办数量增长后响应体过大，前端渲染卡顿；该场景当前不具备可测试性，无法设计分页相关用例。

**建议**

增加 `page` / `page_size` 参数与总数返回，并补充「页码越界」「page_size 超上限」等边界用例。

## BUG-06 密码强度未做校验

| 字段 | 内容 |
| --- | --- |
| 发现阶段 | 设计注册接口参数校验用例时 |
| 严重等级 | 一般 |
| 缺陷类型 | 安全类设计缺陷 |
| 状态 | 已知未修复（演示服务刻意简化） |

**现象**

注册接口只校验密码长度为 6–20 位，对纯数字、纯字母等弱口令不做任何限制，`123456` 可以直接注册成功。

**影响**

与常见生产系统的安全基线不符；对应的高危口令拦截用例无法设计。

**建议**

增加「必须包含字母与数字」「禁止弱口令字典」等规则，并同步补充相应测试用例。
